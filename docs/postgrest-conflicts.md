# Business conflicts without transaction retry loops

An outdated assignment or protected act must return a conflict to its caller. The
database previously raised `40001` for these business rules, which PostgREST 14.5
treated as a retriable serialization failure. Four connections repeatedly called
`rpv_service_assign`, competing for the same locks and filling the error log.

The forward migration changes 16 deliberate error-code assignments in 10 reviewed
functions to `PT409`. It rebuilds their current definitions and preserves every
predicate, lock, signature, security mode, search path and grant. Existing migration
files remain unchanged. Portal and bot handlers accept `PT409`; compatibility with
real/older `40001` responses is retained, without adding an application retry.

Affected workflows: assignment, contractor transitions/reports/files, primary-act
registration and review, cubic metres, payments, owner corrections and internal-task
conflicts. The internal-task bot already handles any database error without retry.
No workflow protection, role, payment, act or user record is changed by this fix.

## Validation and rollout, 2026-11-14

- Full portal test suite, separate internal-task tests, TypeScript, build and Deno
  checks pass. Tests exercise stale writes, role revocation, protected acts, paid
  amounts, idempotency and rollback. The migration is idempotent; tests compare
  complete function definitions and ACLs before/after to ensure only SQLSTATE changes.
- Deploy `rpv-portal` v18 and `smart-api` v131 first; both handle old/new codes.
  Apply `business_conflicts_without_retries` afterwards.
- Read back all deployed Edge files and 10 database function definitions. Only the
  intended code assignments differ, and no manual `40001` remains in public functions.
- Live, deliberately stale assignment and owner-edit calls returned `PT409` inside
  exception blocks, with no business mutation. Hashes of applications, acts,
  published volumes, work history, payout events and order revisions are unchanged.
- The four confirmed retry connections had already ended after the migration.
  A termination request guarded by exact PID, backend start time, database user
  and PostgREST application matched zero sessions; no unrelated session was stopped.
  The subsequent snapshot found zero old retry connections, active assignment RPCs
  or aborted transactions. CPU utilization was not measured.

For another occurrence, correlate PostgreSQL log `parsed.process_id` and context
with `pg_stat_activity`. Do not terminate all authenticator sessions or the schema
listener. Apply the code fix first; stop only exact confirmed looping sessions
that remain. Do not alter real serialization failures generated by PostgreSQL.

Reference: [Supabase troubleshooting guidance](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b).
